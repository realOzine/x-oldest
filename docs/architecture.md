# X Oldest 架构说明

本文描述当前代码的实际结构，不是规划。需求背景见 [spce.md](./spce.md)；本文末尾列出了实现与 spec 不一致的地方。

## 1. 一句话概括

插件往 x.com 页面里注入两个脚本：一个负责"向 X 要数据"，一个负责"把数据存下来、画出来，并跟上 X 的页面切换"。没有后台 Service Worker，没有申请任何权限，所有代码都跑在页面自己的 JS 环境（MAIN world）里。

## 2. 文件与职责

源码是 ES 模块，用 esbuild 打包成两个文件后才被 Chrome 加载。

| 文件 | 行数 | 职责 | 碰不碰 DOM |
| --- | --- | --- | --- |
| `src/engine/main.js` | 12 | 引擎包的入口：装钩子，把接口挂到 `window.__xoldest` | 否 |
| `src/engine/errors.js` | 16 | `XoError`：带种类的错误 | 否 |
| `src/engine/transport.js` | 201 | 请求通道：从 X 借请求上下文，发 GraphQL 请求，把失败分类 | 否 |
| `src/engine/normalize.js` | 194 | 归一化：把 X 的返回整理成统一的帖子、用户对象 | 否 |
| `src/engine/reader.js` | 147 | 读取器：把"只能倒着查"变成"正着读"的算法 | 否 |
| `src/engine/api.js` | 42 | 把上面几个组装成界面要用的两个函数 | 否 |
| `src/ui/main.js` | 11 | 界面包的入口：取到引擎接口后启动界面 | 否 |
| `src/ui/app.js` | 421 | 总控：会话、开关阅读模式、加载循环、缓存、跟随路由 | 少量 |
| `src/ui/view.js` | 179 | 阅读区的 DOM：工具栏、卡片列表、状态栏、点击处理 | 是 |

| `src/ui/page.js` | 96 | 读 X 的页面：识别主页、取主题色、克隆标签 | 只读 X 的 DOM |
| `src/ui/i18n.js` | 60 | 中英文文案和日期格式 | 只读语言 |
| `src/store.js` | 94 | 本地缓存：IndexedDB 里存帖子和阅读进度 | 否 |
| `src/ui/ui.css` | 305 | 样式：隐藏原生时间线、卡片外观 | — |

## 3. 构建与模块连接

### 3.1 构建

`npm run build` 调用 esbuild，从两个入口各打出一个文件：

| 入口 | 产物 | 注入时机 |
| --- | --- | --- |
| `src/engine/main.js` | `dist/engine.js` | `document_start` |
| `src/ui/main.js` | `dist/ui.js` | `document_idle` |

`manifest.json` 引用的是 `dist/` 下的这两个文件和 `src/ui/ui.css`。`dist/` 不进版本库，所以克隆后要先构建一次。开发时用 `npm run watch`，改完源码自动重新打包。产物没有压缩，在浏览器里调试时能直接读。

### 3.2 为什么是两个包

两部分必须在不同的时间运行：

- 引擎要抢在 X 自己的脚本之前，因为它要在 X 发出第一个请求前把钩子装好。
- 界面要等页面基本就绪，因为它一启动就要读页面语言、找标签栏。

如果打成一个包，要么钩子装晚了，要么界面跑早了。

### 3.3 两个包之间唯一的连接

两个包是各自独立的脚本，不能互相 `import`。它们之间只有一个约定：引擎入口把 `{ resolveUser, openReader }` 挂到 `window.__xoldest`，界面入口从那里取。全局空间里只多出这一个名字，源码里也只有两个入口文件碰它。

两个入口还各做一次重复注入检查：引擎发现 `window.__xoldest` 已存在就什么都不做，界面发现已启动过就不再启动。

### 3.4 包内的依赖

包内是普通的 `import` / `export`，依赖只朝一个方向走，没有循环：

```
dist/engine.js                          dist/ui.js

engine/main.js                          ui/main.js
   ├─► transport.js ─► errors.js           └─► app.js ─┬─► view.js ─► cards.js ─► i18n.js
   └─► api.js ─┬─► transport.js                        ├─► page.js ─► i18n.js
               ├─► normalize.js                        └─► store.js
               ├─► reader.js ─► errors.js
               └─► errors.js
```

唯一需要"反向通知"的地方是阅读区里的用户操作（清缓存、点重试、滚到底、点链接）：`view.js` 不导入 `app.js`，而是由 `app.js` 启动时通过 `view.bind({ restart, retry, nearEnd, navigate })` 把四个回调交给它。

## 4. 数据引擎（src/engine/）

### 4.1 transport.js：借而不造

向 X 的内部接口发请求需要四样东西，全部取自 X 自己的运行时：

| 需要的东西 | 怎么得到 | 所在函数 |
| --- | --- | --- |
| 认证头 | 包住 `XMLHttpRequest` 的三个方法，X 每发一个 GraphQL 请求就记下它的头 | `installObserver` |
| feature 开关的取值 | 同一个钩子，从请求的 URL 或 body 里读出并累积 | `observe` |
| 接口的查询 ID、它声明的开关列表 | 扫描 X 的 webpack 模块源码，用正则匹配接口定义 | `loadRuntime` |
| 每次请求的签名 | 同一次扫描里找到 X 的签名模块，直接调用 | `loadRuntime` |

签名只对它所属的那一次请求有效，所以保存的头里特意删掉了它，每次请求现算。CSRF 令牌每次从 `ct0` cookie 现读。这些值只存在内存里。

`gql(name, variables)` 是唯一的出口。所有请求排成一条串行队列，间隔至少 400 毫秒。失败一律抛出带 `kind` 的 `XoError`：

| kind | 含义 |
| --- | --- |
| `incompatible` | X 页面里找不到我们依赖的东西 |
| `auth` | 未登录或会话被拒（401 / 403） |
| `rate` | 被限流（429），附带 `resetAt` |
| `http` | 断网或其他 HTTP 状态 |
| `api` | HTTP 200 但响应体报错 |
| `parse` | 响应读不懂 |
| `unavailable` | 账号不存在或不可读 |
| `cancelled` | 读取器被取消 |

这个分类是"不把失败当成空结果"的基础：界面根据 `kind` 决定显示什么、要不要给重试按钮。

### 4.2 normalize.js：只此一处认识 X 的数据结构

把 X 返回的深层嵌套对象整理成两种扁平对象：

```
用户  { id, name, screenName, avatar, createdAt }
帖子  { id, createdAt, userId, user, segments, media, quoted, quoteMissing, replyTo, counts }
```

这两种对象既是界面的渲染输入，也是缓存里存的内容，所以其他文件都不需要知道 X 的接口长什么样。文件里全是纯函数。

最费事的是正文。`buildSegments` 把正文切成片段（文字 / 链接 / @ / 话题 / 股票代码），界面逐段生成节点，帖子内容从不经过 `innerHTML`。几个细节：

- 实体的位置按码点计，不是按 JS 字符串下标，所以先 `Array.from` 再切，emoji 才不会错位。
- 超过 280 字的帖子，完整正文在 `note_tweet` 里，优先取它。
- 正文末尾 X 自动附加的媒体链接、引用帖链接会被去掉，因为媒体和引用另有独立区块。
- 早期帖子没有链接实体，正文里的裸网址用正则补成链接。

### 4.3 reader.js：核心算法

**问题**：搜索只能回答"某时刻之前最新的若干条"，而用游标深翻会悄悄丢掉最早的几条。

**做法**：读取器从不翻页，而是按时间窗口推进。它维护一个时间游标 `cursor`，表示"这之前的都读完了"。

```
时间轴 ─────────────────────────────────────────────►
        cursor                       cursor + span
          │◄────────── 窗口 ──────────►│
          │   ◄─第3页  ◄─第2页  ◄─第1页      每页都是"until 之前最新的 20 条"
```

`next()` 每次返回一批升序的帖子，内部分三步，对应三个方法：

| 方法 | 做什么 |
| --- | --- |
| `openWindow` | 取窗口的第一页。空的：游标跳到窗口末尾，跨度翻倍。满页却只覆盖了窗口后半段不到一半：说明帖子太密，缩小跨度重来。否则返回一个待填充的窗口 |
| `fillWindow` | 把 `until` 挪到已拿到的最早一条的时间，再取一页，直到拿到不满的一页 |
| `closeWindow` | 整个窗口去重、按时间升序（同一毫秒按 ID）排好，游标前进到窗口末尾 |

三个设计要点：

- **读取器不认识 X**。构造时传入一个 `fetchPage(since, until)` 函数，它只管调用。真正的搜索请求在 `api.js` 里。它只导入 `errors.js` 里的 `XoError`，所以算法可以脱离网络单独测试。
- **状态可续**。全部进度就是 `cursor` 和 `span` 两个数，存进缓存就能续读。
- **中途失败不白费**。填充到一半出错时，已拿到的页留在 `pending` 里，再次调用 `next()` 从断点继续。

### 4.4 api.js

对界面只暴露两个函数：

- `resolveUser(screenName)`：查用户 ID 和注册时间。
- `openReader(user, options)`：返回一个绑定好搜索请求的读取器。

搜索语句是 `from:用户名 since_time:… until_time:… -filter:replies`，只取用户自己发的帖子，不含回复。用秒级的 `since_time` / `until_time` 而不是按天的 `since` / `until`，因为后者的日界线不是 UTC。返回结果里作者不是目标用户的会被丢弃。

## 5. 本地缓存（src/store.js）

IndexedDB 数据库 `x-oldest`，两张表：

| 表 | 主键 | 内容 |
| --- | --- | --- |
| `sessions` | `key`（小写用户名） | 用户资料、时间游标、窗口跨度、阅读锚点、版本号 `rev` |
| `tweets` | `[key, seq]` | 帖子本体；`seq` 是它在阅读顺序中的序号 |

三个保证：

- **帖子和进度一起写**：同一个事务里写入新一批帖子和新的游标，刷新后不会出现"进度已经过去了、帖子却没存上"。
- **多标签页不互相覆盖**：每次写入带上自己上次看到的 `rev`，与库里的不一致就放弃写入。界面收到失败后把该会话标记为 `cacheBroken`，之后不再写。
- **缓存坏了不影响阅读**：所有操作失败时都返回"没有缓存"，而不是抛错。

## 6. 界面（src/ui/）

### 6.1 cards.js：一条帖子一张卡片

用一个十几行的工具函数 `h()` 直接创建 DOM，没有用框架。卡片只负责显示和链接：点赞、回复、转发交给 X 自己的帖子详情页，所以卡片上没有"看起来能点、实际没反应"的按钮。

卡片自己不处理点击。需要跳转的元素带 `href` 或 `data-href`，由 `view.js` 在根节点上统一处理。

### 6.2 page.js：读 X 的页面

所有"依赖 X 的 DOM 长什么样"的代码集中在这里，X 改版时只需要看这一个文件。X 的类名是生成的、每次发版都变，所以只靠 `data-testid`、ARIA 角色和结构来定位。

- `findProfile()`：判断当前是不是用户主页，返回用户名、标签栏、挂载位置。
- `applyTheme()`：读出 X 当前的背景色（浅色 / 暗蓝 / 纯黑）和用户选的强调色，写成 CSS 变量。
- `createTab()`：克隆一个 X 原生的未选中标签并改掉文字，这样字体、间距、悬停效果自动与原生一致。

### 6.3 view.js：阅读区

管理阅读区的全部 DOM，元素引用存在会话的 `s.els` 上。四个出口：

| 函数 | 作用 |
| --- | --- |
| `mount(s, p)` | 确保阅读区存在于页面上；X 重绘把它冲掉后会重建。可重复调用 |
| `renderStatus(s)` | 根据 `s.status` 画状态栏和工具栏里的"最早帖子"提示；加载中时显示占位卡片 |
| `reset(s)` | 清空列表，从阅读位置附近（没有则从第一条）重新开始渲染 |
| `fill(s)` | 把已加载但还没渲染的帖子再往列表末尾补一批；全部渲染完时返回 false |

占位卡片（骨架屏）在挂载时建好，放在状态栏里，加载中由 CSS 显示：列表为空时 5 张，已有帖子时只在末尾显示 2 张。它们不随进度文字重建，所以动画不会被打断。

**懒渲染**。一个会话可能缓存了几千条帖子，一次全放进页面会让浏览器卡死。所以列表里只放 `s.tweets` 的一段 `[first, last)`：

- 起点在阅读位置前 5 条（没有阅读位置就从第一条开始），每次补 30 张。
- 列表下方的状态栏靠近视口时向下补，列表上方的标记元素 `top` 靠近视口时向上补。两者由同一个 `IntersectionObserver` 盯着。
- 观察器只在状态变化时通知。每补完一批就把目标重新观察一次，让它再报告一次当前状态：仍然靠近就继续补，否则停下。这样每帧只做一批，不会长时间占住主线程。
- 向上补时依赖浏览器自带的滚动锚定，屏幕上的内容不会跳。月份标题在接缝处会重新对齐。

滚过的卡片不回收，所以一直往下读，DOM 仍会慢慢变大；屏幕外的卡片靠 CSS 的 `content-visibility: auto` 跳过排版和绘制。

### 6.4 app.js：总控

**会话**。每个访问过的用户主页对应一个会话对象，字段分四组（都在 `getSession` 里声明并注释）：

| 组 | 字段 |
| --- | --- |
| 身份 | `key` `sn` `user` `t0` |
| 加载 | `reader` `tweets` `status` `loading` `done` `waitTimer` |
| 视图 | `els` `near` `lastY` `anchor` `anchorTimer` |
| 缓存 | `skipCache` `cacheChecked` `cacheBroken` `resume` `rev` |

**三个模块级变量**构成一个小状态机：

| 变量 | 含义 |
| --- | --- |
| `sessions` | 所有会话，在本次页面生命周期内保留 |
| `active` | 当前正在显示的会话 |
| `suspended` | 用户离开时暂存的 `{ key, scrollY }`；从帖子详情返回同一主页时据此恢复，去了别处则丢弃 |

**进入与退出**。进入阅读模式只是给 `<html>` 加上 `data-xo-active` 属性，CSS 据此隐藏 X 的原生时间线、显示阅读区。X 的节点一个都不删、不移动，所以退出就是去掉这个属性。

**轮询**。X 是单页应用，页面切换不会重新加载脚本，也不通知任何人。这里没有去追踪它的每种变化，而是每 300 毫秒跑一次 `tick()`：重新识别当前页面，标签不在就补上，阅读区被冲掉就重建，用户离开了就退出。它调用的每个函数都可以重复执行。

**加载循环**。状态栏在列表最下方，被一个 `IntersectionObserver` 盯着（提前 2000px）。它靠近视口时触发 `loadMore`：向读取器要下一批 → 追加到内存 → 写缓存 → 追加卡片 → 状态栏仍在范围内就再来一轮。遇到限流则定时到重置时间后自动继续；标签页隐藏时不加载。

**阅读位置**。记的不是滚动像素，而是"视口顶部那张卡片的 ID 和它距顶部的偏移"。恢复时找到那张卡片再对齐，并在 150 和 500 毫秒后各重对一次，因为卡片高度会随布局稳定而变化。列表是懒渲染的，滚动像素在重建后没有意义，所以刷新页面、从帖子详情返回、X 重绘后重建阅读区，都用这个锚点恢复。

## 7. 一次完整流程

```
用户点「最早」                                   app.js   onOurTabClick
  └─ activate()        加 html 属性、同步主题色     page.js  applyTheme
       ├─ view.mount() 建工具栏、列表、状态栏        view.js
       └─ start()
            ├─ restoreFromCache()  有缓存：立即渲染并滚到锚点        store.js
            ├─ resolveUser()       无缓存：查用户 ID 和注册时间      engine/api.js
            └─ openReader()        起点 = 缓存游标 / 指定月份 / 注册时间
                 └─ loadMore()  ◄──────────────────┐
                      ├─ reader.next()             │  状态栏仍在     engine/reader.js
                      ├─ saveProgress()            │  视口附近       store.js
                      └─ view.fill() ──────────────┘                 ui/cards.js
```

## 8. 值得学习的设计取舍

1. **借而不造**。认证头、开关取值、查询 ID、签名全部来自 X 自己的运行时。X 改版时这些值自动跟着变，代码里没有写死任何一个。
2. **把"会变的东西"关在一个文件里**。X 的接口格式只有 `normalize.js` 认识，X 的页面结构只有 `page.js` 认识，X 的请求方式只有 `transport.js` 认识。
3. **算法与网络分开**。`Reader` 只拿一个"取一页"的函数，不知道背后是搜索接口。
4. **用 CSS 属性切换模式**。进入和退出都只改一个属性，不碰 X 的 DOM，所以"退出后恢复原状"几乎不可能出错。
5. **轮询加幂等，代替事件监听**。看起来笨，但对一个不受自己控制、随时重绘的页面来说，这比追踪它的每种变化更可靠。
6. **错误带种类**。界面能区分"不兼容 / 未登录 / 限流 / 没结果"，而不是统一显示成"没有帖子"。
7. **数据与视图之间只有一种格式**。归一化后的帖子对象既是渲染输入也是缓存内容。

## 9. 与 spec 的差异和已知限制

| 项目 | spec 的要求 | 当前实现 |
| --- | --- | --- |
| 运行环境 | 界面在隔离环境，页面里只留一个窄桥接 | 全部在 MAIN world |
| 缓存位置 | 扩展自己的 IndexedDB | x.com 源下的 IndexedDB，X 清站点数据时会一并清掉 |
| 账号身份 | 用 `user_id` 做键 | 用小写用户名做键；改名或用户名被他人重新注册时缓存会错配 |
| 筛选与起点 | 可切换包含回复、可指定起始日期 | 不提供：只读不含回复的帖子，总是从最早开始 |
| DOM 规模 | 同时挂载不超过 100 张卡片 | 懒渲染，按需每次补 30 张；滚过的不回收 |
| 多标签页 | 共用一个采集任务 | 各自采集，只保证缓存不互相写坏 |
| 窗口结束判定 | 不能因一页不满就认定结束 | 一页少于 18 条即视为窗口结束，代码注释里说明这是为速度做的取舍 |
| 缺口提示 | 跳过的时间段要有明显标记 | 没有缺口标记 |
| 同秒超过一页 | 继续分页或拆分 | 无法再往前推进，该窗口内更早的帖子全部丢失，且没有提示 |
| 测试 | 固定样本覆盖分页和边界 | 仓库里没有测试 |
