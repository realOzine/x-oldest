# X Oldest 架构说明

本文描述当前代码的实际结构，不是规划。需求背景见 [spce.md](./spce.md)；本文末尾列出了实现与 spec 不一致的地方。

## 1. 一句话概括

插件在 x.com 页面里注入三段脚本：一段负责"向 X 要数据"，一段负责"把数据存下来"，一段负责"把数据画出来并跟上 X 的页面切换"。没有后台 Service Worker，没有申请任何权限，所有代码都跑在页面自己的 JS 环境（MAIN world）里。

## 2. 文件与职责

| 文件 | 行数 | 何时注入 | 职责 |
| --- | --- | --- | --- |
| `manifest.json` | 28 | — | 声明两组 content script，都在 MAIN world |
| `src/engine.js` | 481 | `document_start` | 数据引擎：拿到请求上下文、发搜索请求、把返回整理成统一格式、按时间向前推进 |
| `src/store.js` | 100 | `document_idle` | 本地缓存：IndexedDB 里存帖子和阅读进度 |
| `src/ui.js` | 708 | `document_idle` | 页面集成：识别主页、插入「最早」标签、渲染卡片、处理路由和滚动位置 |
| `src/ui.css` | 305 | `document_idle` | 样式：隐藏原生时间线、卡片外观 |

三段脚本通过一个全局对象 `window.__xoldest` 相连：`engine.js` 创建它并挂上 `resolveUser`、`Reader`、`XoError`、`rate`；`store.js` 往上加 `store`；`ui.js` 只读取它。依赖方向是单向的：

```
ui.js ──► store.js ──► engine.js（只借用命名空间）
  │
  └─────────────────► engine.js（Reader / resolveUser）
```

`engine.js` 必须在 `document_start` 注入，因为它要在 X 发出第一个请求之前把钩子装好。

## 3. 数据引擎（engine.js）

引擎内部分四层，自下而上：

### 3.1 请求上下文：从 X 自己的请求里"借"

向 X 的内部接口发请求需要四样东西，引擎都不自己造：

| 需要的东西 | 怎么得到 | 位置 |
| --- | --- | --- |
| 认证头（authorization 等） | 包住 `XMLHttpRequest` 的 `open` / `setRequestHeader` / `send`，X 每发一个 GraphQL 请求就记下它的头 | `engine.js:34-74` |
| feature 开关的取值 | 同一个钩子，从请求的 URL 或 body 里读 `features`，累积合并 | `engine.js:69-73` |
| 接口的查询 ID 和它需要哪些开关 | 扫描 X 的 webpack 模块源码，用正则匹配 `SearchTimeline`、`UserByScreenName` 的定义 | `engine.js:94-125` |
| 每次请求的签名（`x-client-transaction-id`） | 在同一次扫描里找到 X 的签名模块，直接调用它 | `engine.js:105-124` |

签名有时效，必须每次请求现算，所以保存的头里特意删掉了它（`engine.js:66`）。CSRF 令牌每次从 `ct0` cookie 现读（`engine.js:164`）。这些值只留在内存里，不写入缓存。

任何一样找不到都会抛出 `kind: 'incompatible'` 的错误，界面据此提示"与当前 X 页面不兼容"，而不是显示成"没有帖子"。

### 3.2 请求通道

- `enqueue`（`engine.js:137`）：所有请求排成一条串行队列，相邻两次至少间隔 400 毫秒。
- `gql`（`engine.js:151`）：拼 URL、算签名、发请求，并把结果分类成 `rate`（429）、`auth`（401/403）、`http`、`parse`、`api`。每次响应的限流余量记在 `state.rate` 里。

### 3.3 归一化

把 X 返回的深层嵌套结构整理成界面用的扁平对象（`normTweet`，`engine.js:305`）。其中最费事的是正文：`buildSegments`（`engine.js:224`）按码点位置把正文切成"文字 / 链接 / @ / 话题"几种片段，界面只需逐段生成节点，不用拼 HTML，因此不存在注入风险。长帖优先取 `note_tweet` 的完整文本。

`searchWindow`（`engine.js:349`）会丢弃作者不是目标用户的结果，防止推荐或他人帖子混入。

### 3.4 Reader：把"只能倒着查"变成"正着读"

这是整个插件的核心算法（`engine.js:387-473`）。

**问题**：搜索只按从新到旧返回，而且用游标深翻会悄悄丢掉最早的几条。

**做法**：维护一个时间游标 `cursor`，表示"这之前的都读完了"。每次调用 `next()`：

1. 取窗口 `[cursor, cursor + span)`，查一页（最新的 20 条）。
2. 空的：游标直接跳到窗口末尾，窗口跨度翻倍（上限一年），继续。
3. 满页但只覆盖了窗口后半段不到一半：说明这个窗口里帖子太多，把跨度缩小后重来，这样首屏不用等一整个大窗口。
4. 否则开始"回退"：不用游标，而是把查询的结束时间挪到本页最早一条的时间，再查一页，如此反复，直到拿到一页不满的结果。
5. 整个窗口收齐后，按时间升序、同秒按 ID 排序，作为一批返回；游标前进到窗口末尾。

```
时间轴 ──────────────────────────────────────────►
        cursor                    cursor+span
          │◄──────── 窗口 ─────────►│
          │   ◄──第3页 ◄──第2页 ◄──第1页   （每页都是"某时刻之前最新的20条"）
          │
          └─ 收齐后整体升序提交，cursor 移到窗口右端
```

两个细节：

- 回退中途出错（限流、断网）时，已拿到的部分留在 `this.pending` 里，重试时从断点继续，不重查整个窗口。
- 窗口跨度是自适应的：稀疏时变大，密集时变小，并且会随进度存入缓存，下次打开沿用。

## 4. 本地缓存（store.js）

IndexedDB 数据库 `x-oldest`，两张表：

| 表 | 主键 | 内容 |
| --- | --- | --- |
| `sessions` | `key`（小写用户名） | 用户资料、筛选条件、时间游标、窗口跨度、阅读锚点、版本号 `rev` |
| `tweets` | `[key, seq]` | 帖子本体；`seq` 是它在阅读顺序中的序号 |

三个保证：

- **帖子和进度一起写**（`store.js:74`）：同一个事务里写入新一批帖子和新的游标，所以刷新后不会出现"进度已经过去了、帖子却没存上"。
- **多标签页不互相覆盖**：每次写入带上自己上次看到的 `rev`，与库里的不一致就放弃写入。界面收到失败后把该会话标记为 `cacheBroken`，之后不再写。
- **缓存坏了不影响阅读**：所有操作失败时都返回"没有缓存"，而不是抛错。

## 5. 页面集成（ui.js）

### 5.1 跟上 X 的页面变化：轮询

X 是单页应用，页面切换不会重新加载脚本。这里没有监听路由事件或用 `MutationObserver`，而是每 300 毫秒跑一次 `tick()`（`ui.js:642`）：重新识别当前是不是用户主页、标签是否还在、阅读区是否还挂着，缺什么补什么。所有操作都是幂等的，所以 X 重绘掉我们的节点后，下一拍就补回来。

主页识别（`findProfile`，`ui.js:88`）靠 `data-testid` 和标签栏第一个链接的路径，不依赖 X 的类名。

### 5.2 「最早」标签

克隆一个 X 原生的未选中标签改掉文字（`ensureTab`，`ui.js:145`），这样字体、间距、悬停效果自动与原生一致。点击原生标签时在捕获阶段先退出阅读模式。

### 5.3 进入与退出

进入阅读模式只做一件事：给 `<html>` 加上 `data-xo-active` 属性。CSS 据此隐藏 X 的原生时间线、显示我们的 `#xo-root`（`ui.css:2-13`）。X 的节点一个都不删、不移动，所以退出就是去掉这个属性。

三个模块级变量构成一个小状态机：

| 变量 | 含义 |
| --- | --- |
| `sessions` | 每个用户一份会话（已加载的帖子、Reader、筛选条件等），在本次页面生命周期内保留 |
| `active` | 当前正在显示的会话 |
| `suspended` | 用户点进帖子详情时暂存的 `{ key, scrollY }`；从详情返回同一主页时据此恢复，去了别处则丢弃 |

另外用 `sessionStorage` 记一个标志，使刷新页面后自动重新进入阅读模式。

### 5.4 加载循环

列表底部的状态栏被一个 `IntersectionObserver` 盯着（提前 2000px）。它进入范围时调用 `loadMore`（`ui.js:371`）：向 Reader 要下一批 → 追加到内存 → 写缓存 → 追加卡片 → 如果状态栏仍在范围内就再来一轮。遇到限流则定时到重置时间后自动继续；标签页隐藏时不加载。

### 5.5 阅读位置

记的不是滚动像素，而是"视口顶部那张卡片的 ID + 它距顶部的偏移"（`updateAnchor`，`ui.js:316`）。恢复时找到那张卡片再对齐，并在 150 和 500 毫秒后各重对一次，因为卡片高度会随图片加载变化。

### 5.6 卡片

用一个小工具函数 `h()` 直接创建 DOM，没有用框架。点击行为统一在根节点上委托处理（`onRootClick`，`ui.js:622`）：站内链接走 X 自己的路由（`pushState` + 手动触发 `popstate`），选中文字时不跳转，按住 Cmd/Ctrl 开新标签。

没有做虚拟列表，所有卡片都留在 DOM 里，靠 CSS 的 `content-visibility: auto` 让浏览器跳过屏幕外卡片的排版和绘制。

## 6. 一次完整流程

```
用户点「最早」
  └─ activate()            加 html 属性、同步主题色、挂载 #xo-root
       └─ start()
            ├─ restoreFromCache()   有缓存：立即渲染并滚到锚点
            ├─ resolveUser()        无缓存：查用户 ID 和注册时间
            └─ new Reader(...)      起点 = 缓存游标 / 指定月份 / 注册时间
                 └─ loadMore()  ◄───────────────┐
                      ├─ reader.next()          │ 状态栏仍在
                      ├─ saveProgress()         │ 视口附近
                      └─ appendCards() ─────────┘
```

## 7. 值得学习的设计取舍

1. **借而不造**。认证头、开关取值、查询 ID、签名全部来自 X 自己的运行时。X 改版时这些值自动跟着变，代码里没有写死任何一个。
2. **用 CSS 属性切换模式**。进入和退出都只改一个属性，不碰 X 的 DOM，所以"退出后恢复原状"几乎不可能出错。
3. **轮询加幂等，代替事件监听**。看起来笨，但对一个不受自己控制、随时重绘的页面来说，这比追踪它的每种变化更可靠。
4. **错误带种类**。`XoError.kind` 让界面能区分"不兼容 / 未登录 / 限流 / 没结果"，这是 spec 里反复强调的"不能把失败当成空结果"的落地方式。
5. **状态可续**。Reader 的全部进度就是 `cursor` 和 `span` 两个数，存下来就能续读；窗口内的半成品放在 `pending` 里应对中途失败。
6. **数据与视图之间只有一种格式**。归一化后的帖子对象既是渲染输入也是缓存内容，界面完全不知道 X 的接口长什么样。

## 8. 与 spec 的差异和已知限制

| 项目 | spec 的要求 | 当前实现 |
| --- | --- | --- |
| 运行环境 | 界面在隔离环境，页面里只留一个窄桥接 | 全部在 MAIN world |
| 缓存位置 | 扩展自己的 IndexedDB | x.com 源下的 IndexedDB，X 清站点数据时会一并清掉 |
| 账号身份 | 用 `user_id` 做键 | 用小写用户名做键；改名或用户名被他人重新注册时缓存会错配 |
| 筛选隔离 | 不同筛选条件的进度分开保存 | 切换「包含回复」或起始月份会清空该账号的全部缓存 |
| DOM 规模 | 同时挂载不超过 100 张卡片 | 全部挂载，靠 `content-visibility` 减负 |
| 多标签页 | 共用一个采集任务 | 各自采集，只保证缓存不互相写坏 |
| 窗口结束判定 | 不能因一页不满就认定结束 | 一页少于 18 条即视为窗口结束，代码注释里说明这是为速度做的取舍 |
| 缺口提示 | 跳过的时间段要有明显标记 | 没有缺口标记 |
| 同秒超过一页 | 继续分页或拆分 | 视为窗口结束，多出的帖子会丢 |
| 测试 | 固定样本覆盖分页和边界 | 没有测试 |
